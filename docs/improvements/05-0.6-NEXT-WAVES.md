# 05 — Le prossime ondate di FLIP 0.6 (piano)

Stato: **preparate, non avviate** (2026-11-20). Capo ha chiesto «preparami le ondate»; il via per ognuna lo dà lui.
Base: ramo `feat/0.6-tools`, dopo il passo 0 (pnpm, commit `ed4ca8c`). Nessun push, nessuna `.app`/`.dmg`.

## 1. Come girano le ondate

- Formato `/assign`: `.assign/RULES.md` + `P1.md … Px.md` (cartella ignorata da git), un solo prompt in inglese uguale per
  tutti, da cui cambia solo la cifra dell'ultima riga. I modelli li lancia Capo; nessun subagente sotto `/assign`.
- **Una ondata alla volta.** `RULES.md` è uno solo e la base cambia a ogni unione, quindi i file `.assign/` della
  ondata N+1 si scrivono quando la N è fusa e verificata (questo documento è il piano da cui si generano).
- Dentro un'ondata ogni file condiviso (registri in `engines/mod.rs`, `i18n.ts`, liste di token) ha **un solo
  proprietario**. I Px che dipendono da altri aspettano la loro unione.
- Controlli per i modelli: typecheck, clippy e i soli test dei file toccati, per percorso. **La suite intera la lancia
  solo il lead**, una per volta, dopo le unioni (`pnpm exec tsc --noEmit`, `bun test`, `cargo clippy --all-targets -- -D
  warnings`, `cargo test`, swiftc typecheck, `./scripts/audit-repository.sh`).
- Dopo ogni Px verificato: unione `--no-ff`, suite, commit, pulizia automatica (worktree, `side/*`, Px).
- Il lato visivo (ruota, Aura, anteprima) non si può provare da qui: resta in `ACCEPTANCE.md` per Capo.
